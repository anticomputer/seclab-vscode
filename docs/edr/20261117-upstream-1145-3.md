## Context
microsoft/vscode published security advisories on 2026-11-10 that affect every release before
1.145.3. We pinned 1.145.0 (`a717861c`). 1.145.3 (`dcd3ad6e`) is a patch release, 44 commits on
the 1.145 branch. 1.146.0 also exists; it is a feature release and is sized separately.

## Decision
- **Pin 1.145.3** in `upstream.lock` and the dependency register. The whole patch queue (22
  patches) applies unchanged. The only file both upstream and the queue change is
  `configurationService.ts` (patch 0017). Upstream's new rules there harden workspace and folder
  settings in untrusted workspaces; 0017 closes REH-supplied remote user settings in trusted
  `seclab+` windows. They don't interact, and 0017 is still needed (review UB).
- **RPC policy:** the inventory is regenerated from 1.145.3, and the policy is re-pinned by a
  tool (`rpc-filter/tools/repin_policy.py`) that refuses if any file the policy cites changed
  upstream. The API surface was identical. The drift check now fails unless the inventory is of
  the SHA `upstream.lock` pins (UB-1), so a bump can't be certified against the old inventory.
- **Per-build tab images:** `./seclab template sbx seclab-tab:b-NAME` and
  `./seclab image oci --tag b-NAME` build proof images that never replace the shared `:local`
  tags other sessions use. Runners take them through `SECLAB_TAB_IMAGE`, validated by the
  harness. `clean-host` keeps `b-` tags for 7 days.
- **Build tree hygiene:** moving a build volume to a new pin left the files earlier patches had
  added, so patch 0005's new files failed to apply. `fetch-upstream.sh` now makes the tree
  exactly the pinned commit: the index is rebuilt, every untracked file is cleaned, and the
  script fails if anything still differs. The install stamp covers every lockfile and the
  upstream commit (review FU).

## Proof
- `patch-build` (upstream typecheck of the patched tree and the reach check) passes, as do
  ci-linux and the headless driver.
- Containment, on per-build images: OCI 107/110 and sbx 120/121, with known expected failures
  only. The canary run is clean on both drivers. A 1.145.0 baseline gives the same results.
- Level B on macOS, with the attested build-macos app from this branch. The result matches the
  1.145.0 baseline. Both runs exposed a harness gap: on a filtered build, `[fsmonitor]` can't
  run, because the git extension's resource-trust request is denied in tabs. That is fixed
  separately (review FXF).

## Consequences
- 1.146.0 needs its own bump, with a patch-queue rebase.
- A later bump follows the same steps: pin, apply the queue, regenerate the inventory and
  re-pin, build, prove on per-build images, review, then this record's successor.
