# Per-tab CA: generated at broker start, private key only on the broker's tmpfs

- **Status:** accepted
- **Date:** 2026-11-04
- **Deciders:** broker session
- **Related:** [ADR no real secret enters a tab](../adr/20261104-no-real-secret-enters-a-tab.md)

## Context
To see inside HTTPS, the broker has to terminate TLS, which means the tab
must trust a CA. If one CA were shared across tabs, its key would let one
tab's broker impersonate any site to every other tab, and a leaked key would
be long-lived.

## Decision
- **One CA per broker start.** `make_ca`
  ([__main__.py](https://github.com/anticomputer/seclab-vscode/blob/b34dfb907f2550e1eae792253a4086cf844b2bae/broker/seclab_broker/__main__.py#L29))
  calls mitmproxy's `CertStore.create_store`: RSA-2048, `CN=seclab-vscode tab
  CA <tabId>`, `O=seclab-vscode broker`.
- **Key storage.** The key is written to `/run/seclab/ca/mitmproxy-ca.pem`,
  mode 0600 under a 0700 directory, on a **tmpfs**. The container runs with a
  read-only root filesystem, so the key never reaches disk. The PKCS#12 and
  `.cer` bundles mitmproxy also writes are deleted at once.
- **Public certificate only.** It is exported over `ca.get`, and optionally to
  `$SECLAB_CA_EXPORT_DIR/ca.pem`. The supervisor installs it in the tab:
  - into the system store, as root at creation time;
  - via `NODE_EXTRA_CA_CERTS`;
  - via `REQUESTS_CA_BUNDLE` and `SSL_CERT_FILE` pointing at the system
    bundle;
  - git uses the system store.
- **Upstream verification** stays on, against certifi. A test-only environment
  variable can *add* a CA; it never replaces certifi.
- **Process hardening.** The broker process is non-dumpable and has
  `RLIMIT_CORE=0`, so a same-uid `docker exec` cannot read the key out of
  memory.

## Alternatives considered
- **A long-lived CA in the keychain, shared by all tabs:** rejected because of
  the blast radius and lifetime.
- **Name-constrained CA:** desirable but deferred, because mitmproxy's
  `create_ca` doesn't add NameConstraints. Recorded as an open issue.
- **A CA generated by the supervisor and passed in:** rejected. The private
  key would leave the broker.

## Consequences
- A tab's trust in its CA ends when the broker restarts, and the supervisor
  re-installs the new certificate. Clients that pin certificates fail closed
  and need a non-MITM path or a deny.

## Evidence
- `test_broker_process_custody` checks:
  - the key line is `-rw-------`;
  - there are no `.p12` files;
  - `/run/seclab` is tmpfs;
  - the workspace certificate equals `ca.get` and contains no private key;
  - `/proc/1/environ` and `/proc/1/mem` are unreadable;
  - the core limit is `0 0`.
- `create_store` and `create_ca` at
  [mitmproxy certs.py](https://github.com/mitmproxy/mitmproxy/blob/51c1d6b2d8d3367a773411eb7a3eeccec82b3ea7/mitmproxy/certs.py).
