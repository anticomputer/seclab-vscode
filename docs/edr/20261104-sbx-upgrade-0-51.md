# sbx upgraded to 0.51.0: findings

- **Status:** accepted
- **Date:** 2026-11-04
- **Deciders:** anticomputer (approved the upgrade); fork-build session
- **Related:** [ADR pluggable provider](../adr/20261104-pluggable-sandbox-provider.md), [ADR single broker](../adr/20261104-single-broker-sbx-fence.md)

## Context
The host had sbx v0.39.0. The docs describe newer features (HTTP method and
path rules, optional workspace paths). We need a known sbx version to build
`SbxProvider` against.

## Decision
Upgrade through the **same channel it was installed from**, the Homebrew cask
`docker/tap/sbx`, to **v0.51.0**. Build and test `SbxProvider` against 0.51.
Record the minimum version in the provider, and check it at runtime.

## Findings (0.51.0)
- Install channel: `brew info --cask docker/tap/sbx` showed `0.39.0 → 0.51.0`.
  Upgraded with `brew upgrade --cask docker/tap/sbx`, which touched only that
  cask; Homebrew also ran its routine cache cleanup.
- Verbs used by the provider: `create`, `exec -i` (docker-exec semantics,
  `-u`, `-e`, `-w`), `stop`, `rm --force`, `ls --json`, `ports`,
  `policy allow|deny|rm|ls|log`, `secret set-custom`, `template load|ls`.
- The `shell` agent "now ships as a kit" (`docker.io/sbx/shell:latest`).
  Inside, the user is `agent` (uid 1000) in groups `sudo` and `docker`, with
  `/var/run/docker.sock` present. That is VM-local; the VM is the boundary.
  The image includes `socat`, `curl`, `node`, `git` and `python3`.
- sbx injects `HTTP(S)_PROXY` and lowercase `http(s)_proxy` pointing at
  `gateway.docker.internal:3128`, `NO_PROXY=localhost,127.0.0.1,::1,gateway.docker.internal`,
  and `PROXY_CA_CERT_B64`.
- **Policy layers:** a global `default-deny-all` plus a global `local-policy`.
  On this host the latter is "balanced", with 187 allows such as
  `api.anthropic.com:443`. Per-sandbox rules sit on top, and **deny beats
  allow**. A per-sandbox deny narrows a global allow (verified).
- **Secrets:** `secret set-custom` still binds by `--host` (exact or wildcard)
  only. `--header`/`--format` apply only with `--cloud`. No method or path
  binding was found, so the ADR's rejection of sbx-as-engine still holds.
- **New:** `policy allow network --method/--path/--query` (HTTP rules) and
  `policy approval ls|inspect|respond`. Whether an approval **holds** the flow
  or denies-then-retries is not yet tested. TODO: spike this for the broker
  session.

## Alternatives considered
- **Stay on 0.39**: rejected. It is older than the documented features and the
  CLI showed an update notice.
- **Install from a different channel (direct download)**: rejected. Keep the
  user's existing channel.

## Consequences
- `SbxProvider` assumes ≥ 0.51 flag names (`--no-progress`, `--force`).
- The global policy is shared with the user's other sandboxes; see the
  [fence EDR](20261104-sbx-fence-spike.md).

## Evidence

```
$ sbx version            # before
sbx version: v0.39.0 def8cb0523a77e757bdd6ef52b459fe374f3783e
$ brew upgrade --cask docker/tap/sbx && sbx version

$ sbx policy ls

```
