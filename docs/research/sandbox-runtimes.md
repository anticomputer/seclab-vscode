# Sandbox Runtimes for Per-Window VS Code REH Isolation — Comparative Research Report

**Scope note on dates:** Live web lookups in this research environment resolve to a present date of **2026-11-04**. Several CVE IDs cited below (`CVE-2026-xxxxx`) are therefore current, not typos. Each claim is tagged **[VERIFIED]** (confirmed against an official doc/source) or **[INFERRED]** (reasonable deduction not explicitly stated in a primary source).

## 1. Docker Sandboxes (`sbx`)

**(a) Isolation.** Hypervisor isolation: each sandbox is a separate microVM with "no shared memory or processes with the host," plus four more layers — network, Docker-Engine, workspace, and credential isolation — docs.docker.com/ai/sandboxes/security/. **[VERIFIED]** No public CVE/escape history was found for `sbx` itself (product is new); feedback tracked at github.com/docker/sbx-releases/issues (docs.docker.com/ai/sandboxes/).

**(b) Platform/licensing.** macOS (Sonoma 14+, Apple silicon), Windows 11 (64-bit, Windows Hypervisor Platform), Linux (Ubuntu 24.04+, needs KVM + user in `kvm` group) — docs.docker.com/ai/sandboxes/install/. **[VERIFIED]** "The `sbx` CLI and local sandbox compute are free to use, including for commercial work"; cloud compute is pay-as-you-go — docs.docker.com/ai/sandboxes/ (top of page). **[VERIFIED]** sbx itself is closed-source (binary CLI, releases at docker/sbx-releases), unlike the other entries here. **[INFERRED from release-repo structure]**

**(c) Mount/perf.** Direct bind/passthrough mount at the same absolute host path, read-write by default, or read-only `--clone` mode with a private in-VM clone; virtiofs caching is **on by default** for directly mounted workspaces "on all operating systems," reducing round-trips for `git status`/directory scans, disable via `DOCKER_SANDBOXES_ENABLE_VIRTIOFS_CACHE=0` — docs.docker.com/ai/sandboxes/architecture/. **[VERIFIED]** Explicit warning against network-attached/remote-storage workspaces due to passthrough latency. **[VERIFIED]** File-watching: not explicitly documented, but direct virtiofs passthrough with host-visible changes ("changes in either direction are instant with no sync process") implies native inotify-style watching works; **[INFERRED]** — needs hands-on verification for VS Code's recursive watcher specifically.

**(d) Network policy.** All outbound TCP forced through a host-side forward proxy enforcing a policy (Open/Balanced/Locked-Down presets, allow/deny rules, HTTP method/path/query-level "L7" rules) — docs.docker.com/ai/governance/local/. **[VERIFIED]** Policy is runtime-mutable without sandbox restart: `sbx policy allow network <host>` is documented as something you run against an already-running sandbox ("From another terminal… `sbx policy allow network registry.npmjs.org`") — docs.docker.com/ai/sandboxes/get-started/. **[VERIFIED]** UDP blocked by default (opt-in experimental), ICMP always blocked — docs.docker.com/ai/governance/local/.

**(e) Credential injection.** Built-in: the host-side proxy injects real credential values as HTTP headers in place of a "sentinel" placeholder value the agent sees; "the real credential stays outside the sandbox throughout the request" — docs.docker.com/ai/sandboxes/architecture/ and docs.docker.com/ai/sandboxes/security/. **[VERIFIED]** This is close to the "no SSH agent, no ambient credentials, broker on demand" model the user wants.

**(f) API/CLI.** `sbx run|create|ls|stop|rm|prune|exec|cp|policy|mcp|secret|setup ssh|move` — docs.docker.com/ai/sandboxes/usage/, docs.docker.com/ai/sandboxes/integrations/. **[VERIFIED]** Port/stdio reachability: ports can be published to host addresses (`sbx run --publish`, referenced in docs.docker.com/ai/sandboxes/cloud/local-vs-cloud/ comparison table: "Binds sandbox ports to host addresses and ports" for local), and **SSH access** is first-class — `sbx setup ssh` makes each sandbox reachable at `<name>.sbx` as a normal SSH host, which VS Code's own Remote-SSH extension can target directly — docs.docker.com/ai/sandboxes/integrations/. **[VERIFIED]** This SSH surface is a very good fit for carrying the VS Code remote protocol (REH listens on a port/socket inside the sandbox; SSH port-forwards or a Remote-SSH-style tunnel reaches it) — **[INFERRED mapping to the user's architecture]**. There is also a documented cloud-sandbox "Sandboxes API and SDK" for programmatic create/exec (docs.docker.com/ai/sandboxes-api/, not fetched in depth here).

**(g) Latency/resource cost at 5–20 windows.** Not quantified in docs with hard numbers; qualitative claim: "Subsequent runs reuse the cached image and start in seconds" (docs.docker.com/ai/sandboxes/get-started/). **[VERIFIED, directional only]** No published memory/CPU-per-sandbox figures were found; each sandbox is a full microVM with its own Docker Engine and image cache (not shared across sandboxes), so per-window overhead is non-trivial — "each sandbox consumes disk space for its VM image, Docker images, container layers, and volumes" (docs.docker.com/ai/sandboxes/architecture/). **[VERIFIED]** 20 concurrent microVMs each running a private Docker Engine is likely to be the heaviest footprint of all options compared here. **[INFERRED]**

**(h) Maturity.** New commercial product (2025–2026 era), actively documented, Docker-backed, org governance features suggest enterprise intent, but short track record and closed-source core. **[INFERRED from doc freshness/versioning, e.g. "`sbx` version 0.42.0," "v0.48.0"]**

**(h) Maturity.** Very new (macOS 26 ties it to an OS released in 2026); active development, Apple-maintained, versioned as "product versions, not semantic versions," with explicit note that `cluster` and other features are "experimental" — github.com/apple/container README "Project Status". **[VERIFIED]** Strong engineering pedigree (Apple), but single-platform and young.

## 6. Firecracker and Cloud Hypervisor (bare VMMs)

## 8. WSL2

## 9. bubblewrap + Landlock + seccomp (Linux-native, no VM)

**(a) Isolation.** Namespace-based (mount, PID, user namespaces), not hypervisor: "bubblewrap is not a complete, ready-made sandbox with a specific security policy... the level of protection... is entirely determined by the arguments passed to bubblewrap" — github.com/containers/bubblewrap README. **[VERIFIED]** It explicitly disclaims being a security boundary by itself and places the burden of policy design on the caller (e.g., Flatpak, or our own provider code). **[VERIFIED]** Landlock adds unprivileged, in-process, LSM-enforced filesystem-access restriction ("stackable LSM… makes it possible to create safe security sandboxes... empowers any process, including unprivileged ones, to securely restrict themselves" — landlock.io). **[VERIFIED]** seccomp-bpf restricts syscalls. Escape history: bubblewrap has at least one serious, recent, CVSS-8.8 advisory — *CVE-2026-87766*, a symlink-following flaw in sandbox setup (pre-0.12.0) letting a local attacker make bubblewrap write files outside the sandbox onto the host before the sandboxed process even starts, tracked as GHSA-pxhw-h44j-8pfx on github.com/containers/bubblewrap/security/advisories, with Red Hat/Mageia/Rocky distro advisories corroborating — surfaced via search; the GHSA URL is a strong primary-source lead worth a direct fetch to confirm exact wording. **[Corroborated via search across multiple vendor trackers; GHSA link itself not independently re-fetched in this pass — recommend confirming directly]**

**(b) Platform/licensing.** bubblewrap: LGPL, Linux-only — github.com/containers/bubblewrap. **[VERIFIED]** Landlock: Linux kernel feature (mainlined), Linux-only — landlock.io. **[VERIFIED]** seccomp: Linux kernel feature, Linux-only. Combined, this stack is **Linux-native only** — no macOS/Windows path; this is precisely why VS Code's own agent sandboxing and Anthropic's `srt` both pick *different* primitives per OS (Seatbelt on macOS, bubblewrap on Linux) rather than trying to run bubblewrap everywhere. **[INFERRED, consistent with both VS Code's and Anthropic's documented per-OS designs]**

**(c) Mount/perf.** bubblewrap uses `--ro-bind`/`--bind` to construct the sandbox's filesystem view directly from host paths inside a fresh mount namespace — github.com/containers/bubblewrap README "Usage" example. **[VERIFIED]** Since there's no VM and no virtio-fs/9p layer, this is **native bind-mount performance and native inotify file-watching** — the best filesystem/file-watching story of any option in this report, at the cost of weaker isolation. **[VERIFIED mechanism; performance conclusion INFERRED but well-grounded]**

**(d)-(e)** No built-in network-policy proxy or credential broker in bubblewrap/Landlock/seccomp themselves — these are exactly the primitives Anthropic's `srt` (§10) and VS Code's own sandboxing (§11) wrap with policy and (in srt's case) a network allow/deny layer.

**(f) API/CLI.** `bwrap <flags> <command>` — a single exec-style command, easy to drive programmatically, but no daemon/lifecycle manager (create/start/stop/exec/list is left to the caller). **[VERIFIED from README usage example]**

**(g) Latency/cost.** Process-level, essentially instant (no VM boot); resource cost per "sandbox" is just the process's own memory/CPU, since there's no hypervisor overhead. **[INFERRED from the namespace-based architecture]** This makes it the cheapest option for 5-20 concurrent "windows" by a wide margin, at the cost of being the weakest isolation boundary considered (shared host kernel attack surface).

**(h) Maturity.** Very mature, widely deployed as Flatpak's sandboxing core and distro-packaged everywhere; the 2026 CVE shows it's still actively audited and patched, which is a maturity-positive signal even though it's also a reminder the boundary is porous. **[VERIFIED]**

## 10. macOS Seatbelt (`sandbox-exec`) — OpenAI Codex CLI and Anthropic `sandbox-runtime` (`srt`)

**(a) Isolation.** MAC (Mandatory Access Control) policy enforcement via the kernel's Sandbox.kext/Seatbelt profile language (SBPL), not a VM and not namespaces. Both OpenAI's Codex CLI and Anthropic's `srt` use it the same way: dynamically generate an SBPL profile per invocation and run the target process under `sandbox-exec`.
- **Codex CLI**: implementation is in `codex-rs/sandboxing/src/seatbelt.rs` plus companion `.sbpl` policy files (`seatbelt_base_policy.sbpl`, `seatbelt_network_policy.sbpl`, `seatbelt_preferences_policy.sbpl`, `seatbelt_read_only_platform_defaults.sbpl`) in the `openai/codex` repo — confirmed the file exists (1105 lines) at github.com/openai/codex/blob/main/codex-rs/sandboxing/src/seatbelt.rs (page metadata "1105 lines (1026 loc) · 41.1 KB" rendered even though GitHub's anti-bot page blocked full content fetch). **[VERIFIED path/existence; full source content not independently read in this pass — recommend a direct `curl`/`gh api` pull of the raw file for a future deep-dive]**
- **Anthropic `srt`**: "macOS: Uses `sandbox-exec` with dynamically generated Seatbelt profiles" — github.com/anthropics/sandbox-runtime README, "How It Works". **[VERIFIED]**
Known limitations/escape history of Seatbelt itself: Seatbelt/`sandbox-exec` has had multiple documented bypasses over the years in the broader macOS security research community (it's officially deprecated by Apple for third-party use, though still used internally and by these two projects); no specific CVE for Codex's or srt's *use* of it was found, but the underlying primitive's general fragility (profile bugs, kernel-extension bugs) is a known category risk, not something either vendor claims is airtight. **[gap — no specific CVE found for this generation's use; general category risk inferred from Seatbelt's well-known reputation, not independently sourced here]**

**(b) Platform/licensing.** Both macOS-only for this specific mechanism. Codex CLI is Apache-2.0 (github.com/openai/codex README footer: "licensed under the Apache-2.0 License"). **[VERIFIED]** Anthropic `sandbox-runtime` is explicitly "Apache 2.0" per web-search summary of its license badge and is installed via `npm install -g @anthropic-ai/sandbox-runtime` — github.com/anthropics/sandbox-runtime. **[VERIFIED from fetched README]**

**(c) Mount/perf.** Not a mount mechanism at all — Seatbelt/`srt` run **directly on the host filesystem** with read/write restricted by SBPL path rules (no VM, no virtiofs/9p, no copy). `srt`'s filesystem model: "deny-then-allow" for reads (`denyRead` broad, `allowRead` carve-outs, with `allowRead` taking precedence) and the reverse precedence for writes (`denyWrite` beats `allowWrite`) — github.com/anthropics/sandbox-runtime README "Dual Isolation Model". **[VERIFIED]** Because there's no VM layer, file-watching is **native and immediate** — the best possible story for an editor's file watcher, matching bubblewrap's advantage on Linux. **[INFERRED from "no VM" architecture]**

**(d) Network policy.** `srt` has first-class **allow/deny domain lists** enforced via the OS primitive plus "proxy-based network filtering" (github.com/anthropics/sandbox-runtime README top summary: "`srt` uses native OS sandboxing primitives... and proxy-based network filtering"). **[VERIFIED]** Example: `srt --network-allow anthropic.com "curl anthropic.com"` blocks everything else by default — github.com/anthropics/sandbox-runtime (web-search-rendered example, consistent with the fetched README's "Basic Usage" examples showing the same allow/deny curl pattern). **[VERIFIED]** Whether policy can change at runtime without restarting the *process* is unclear: since `srt` wraps a single process invocation (not a long-lived daemon/VM you reconfigure), each policy change would mean re-launching the wrapped process under a new profile — this is architecturally different from Docker Sandboxes' "same running microVM, live proxy policy update." **[INFERRED from the per-invocation wrapper design]** Codex CLI similarly has a `seatbelt_network_policy.sbpl` suggesting static, profile-compile-time network rules per sandboxed command rather than a live-updatable daemon policy. **[INFERRED from filename]**

**(e) Credential injection.** `srt` has no sentinel/broker model documented; it has a different but related feature — **credential masking** (hiding/redacting sensitive values from env vars/files reachable by the sandboxed process) — summarized in the search result and consistent with the "Filesystem Isolation" / `denyRead: ["~/.ssh"]` example in the README ("`srt "cat ~/.ssh/id_rsa"` → Operation not permitted"). **[VERIFIED from fetched README example]** This is a deny-access model, not Docker Sandboxes' intercept-and-substitute model.

**(f) API/CLI.** Both are **single-shot process wrappers**, not daemons: `codex` launches sandboxed subprocesses as part of its own agent loop; `srt "<command>"` wraps any one command (including, interestingly, a documented pattern for wrapping an MCP server's `command`/`args` in `.mcp.json` — github.com/anthropics/sandbox-runtime README "Example Use Case: Sandboxing MCP Servers"). **[VERIFIED]** Neither exposes a create/start/stop/exec/port-forward **lifecycle API** for a long-running service like a REH process — you'd have to invoke `srt node ./rehServer.js` and manage the resulting PID/stdio yourself; there's no notion of "the sandbox" as a reusable addressable object the way Docker Sandboxes, `container`, or microVM tools have. **[INFERRED from the wrapper-only architecture shown in the README]** This is a material gap against requirement (f) in the brief.

**(g) Latency/cost.** Essentially zero extra cost beyond the wrapped process — no VM boot, no daemon — the lightest-weight option of all besides bubblewrap/Landlock/seccomp alone. **[INFERRED from architecture]**

**(h) Maturity.** Both explicitly labeled early/experimental: Anthropic's own README calls `srt` a "Beta Research Preview... APIs and configuration formats may evolve" (github.com/anthropics/sandbox-runtime). **[VERIFIED]** Windows support for `srt` is separately marked "(alpha)" using a dedicated local user account + Windows Filtering Platform + NTFS ACLs — github.com/anthropics/sandbox-runtime README "How It Works". **[VERIFIED]** Codex CLI is production-shipping (OpenAI's main coding-agent CLI) but its sandboxing code specifically wasn't independently audited for a public CVE history in this pass. **[gap]**

## 13. GitHub's agentic-workflow firewall (`gh-aw-firewall` / `awf`) and GitHub Actions / Copilot coding-agent sandboxing

**(a) Isolation.** `awf` is explicitly a **network-policy layer**, not a workload-isolation layer by itself: "`awf` runs your command inside a Docker sandbox with three containers: Squid proxy (filters outbound traffic by domain allowlist) — Agent (runs your command; all HTTP/HTTPS routed through Squid) — API proxy sidecar (holds LLM API keys so they never reach the agent process)" — github.com/github/gh-aw-firewall README. **[VERIFIED]** This is architecturally the closest open-source analogue to Docker Sandboxes' "host-side proxy + sentinel credential" design, and is directly reusable as **the network-policy-proxy component** of a custom `SandboxProvider`, independent of whichever VM/container layer holds the workspace.

## Recommendation

### Primary runtime for the macOS-first prototype: **Apple Containerization / `container` CLI, with Docker Sandboxes' `sbx` as the pragmatic fallback if macOS-26-only is unacceptable**

Reasoning:
- It is the only option in this survey that gives **one real hypervisor VM per window on Apple silicon, built on Apple's own first-party Virtualization.framework**, with a documented, open-source (`apple/containerization`) implementation, sub-second boot claims, virtio-fs sharing, and a CLI (`container run -p/--publish-socket/--mount`) that maps cleanly onto "reach the REH port or a stdio pipe from the host" — github.com/apple/container docs/command-reference.md. **[VERIFIED]**
- Its weaknesses are real and specific: **macOS 26 only** (a hard floor that may be unacceptable if the prototype needs to run on current developer laptops today), and **no built-in egress-policy proxy or credential broker** — both of which the user explicitly wants (deny-by-default network, sentinel credentials). Those two features would have to be built by the team, most efficiently by reusing `gh-aw-firewall`'s Squid+API-proxy-sidecar pattern (github.com/github/gh-aw-firewall) as a design template, ported to sit in front of each `container` VM's network namespace.
- **If the macOS-26 floor is a blocker**, **Docker Sandboxes (`sbx`)** is the better-fitting off-the-shelf alternative *today*: it already ships exactly the network-policy-proxy + sentinel-credential-injection + MCP-gateway model the brief describes, on macOS/Windows/Linux, with an SSH-based integration path VS Code's Remote-SSH client can target directly (docs.docker.com/ai/sandboxes/integrations/). Its costs are a closed-source core, a newer/shorter track record, and materially heavier per-window resource use (one Docker Engine + one microVM per window) — a real concern at 20 concurrent windows.

### Cloud runtime leg: **E2B or a custom Firecracker-based provider (Kata/Cloud Hypervisor/microsandbox as building blocks), or simply Docker Sandboxes' own cloud mode**

- If the team wants a managed, SDK-first cloud sandbox with a mature create/exec/persist API, **E2B**'s Firecracker-microVM model is the cleanest off-the-shelf fit, at the cost of being cloud-only (no self-hosted/offline path) and having the weakest independent verification in this report (several claims were only confirmed via secondary summaries, not a direct repo read — flagged above).
- If the team wants to stay inside Docker's own stack end-to-end, **Docker Sandboxes' cloud mode** (`sbx --cloud`) reuses the identical CLI/policy/credential model as the local provider, which is attractive specifically *because* it lets the same `SandboxProvider` implementation (see below) talk to both backends with minimal branching — docs.docker.com/ai/sandboxes/cloud/local-vs-cloud/.
- For a fully self-hosted cloud/Kubernetes deployment, **Kata Containers** is the natural "VM-per-pod" primitive already built for Kubernetes multi-tenancy — but its **dense, recent, guest-to-host escape-CVE history** (§5) means it should only be adopted with very conservative, locked-down annotation policy and an aggressive patch cadence; it is not a "set and forget" choice for this threat model.

### Linux-native lightweight runtime (developer laptop, Linux-first users): **devcontainers (Docker/Podman) + gVisor (`runsc`)**, with `gh-aw-firewall`-style network policy layered on top

- This gets Linux developers a VM-free, fast-starting, native-bind-mount (hence native file-watching) sandbox, upgraded from bare namespaces to gVisor's user-space kernel for meaningfully better syscall-level isolation than plain `runc` — at the acknowledged cost of gVisor's own disclosed escape history (§4/§5-adjacent) and per-syscall performance overhead. Pure **bubblewrap+Landlock+seccomp** is a leaner alternative if the team is comfortable owning policy construction directly (as VS Code's own Linux sandboxing already does) and accepts the weaker, namespace-only boundary plus its own recent CVE (CVE-2026-87766).
- **Do not** rely on WSL2 or Podman-machine's VM boundary alone as "the" isolation layer on Windows/Linux-desktop paths; both Microsoft's own VS Code sandboxing docs and GitHub's MXC docs explicitly treat the VM as a *substrate* and still layer bubblewrap/Seatbelt-class policy enforcement *inside* it (§11) — the same two-tier pattern should be followed here.

### `SandboxProvider` interface shape

```ts
interface SandboxHandle {
  id: string;
  workspacePath: string;     // host path mounted/shared into the sandbox
}

interface SandboxProvider {
  // lifecycle
  create(opts: {
    workspacePath: string;           // host folder to mount for this window
    mountMode: "rw" | "ro-clone";    // direct bind vs. Docker-Sandboxes-style clone mode
    image?: string;                  // REH base image/template
    resources?: { cpus?: number; memoryMiB?: number };
  }): Promise<SandboxHandle>;

  start(handle: SandboxHandle): Promise<void>;
  stop(handle: SandboxHandle): Promise<void>;
  remove(handle: SandboxHandle): Promise<void>;

  // process + connectivity (the REH bridge)
  exec(handle: SandboxHandle, cmd: string[], opts?: { cwd?: string; env?: Record<string,string> }): Promise<ExecResult>;
  startRehServer(handle: SandboxHandle): Promise<{ port: number } | { stdioPipe: string }>;
  forwardPort(handle: SandboxHandle, containerPort: number): Promise<{ hostPort: number } | { sshTarget: string }>;

  // scope expansion at runtime (the "grant a folder / allow a domain / allow a token" prompts)
  mountAdditionalPath(handle: SandboxHandle, hostPath: string, opts?: { readonly?: boolean }): Promise<void>;
  allowNetworkDestination(handle: SandboxHandle, rule: { host: string; methods?: string[]; paths?: string[] }): Promise<void>;
  grantCredential(handle: SandboxHandle, cred: { name: string; brokerStrategy: "sentinel-header" | "env-inject" | "deny-read-exception" }): Promise<void>;

  // policy introspection, for the approval-prompt UI
  getNetworkPolicy(handle: SandboxHandle): Promise<PolicyRule[]>;
  getMountedPaths(handle: SandboxHandle): Promise<string[]>;
}
```

Backing implementations:
- **`AppleContainerProvider`** — wraps `container run/exec/stop`, implements `allowNetworkDestination`/`grantCredential` via a sidecar proxy process the provider manages itself (not native to `container`).
- **`DockerSandboxesProvider`** — thin wrapper over `sbx create/run/exec/policy/secret/mcp`, where `allowNetworkDestination` and `grantCredential` map almost 1:1 onto `sbx policy allow network` and `sbx secret set`, and `forwardPort` maps onto `sbx setup ssh` + `<name>.sbx`.
- **`CloudSandboxProvider`** — targets either `sbx --cloud` or E2B's SDK; `forwardPort` becomes "expose a public HTTPS URL" per docs.docker.com/ai/sandboxes/cloud/local-vs-cloud/, so the REH bridge needs a tunnel/relay variant rather than a raw TCP forward.
- **`LinuxNativeProvider`** — wraps devcontainer CLI + gVisor `runsc` (or raw bubblewrap/Landlock/seccomp for a lighter variant), with `allowNetworkDestination` implemented via an injected Squid/iptables layer modeled on `gh-aw-firewall`'s container trio.

### Key trade-offs to carry forward
1. **macOS-26-only vs. today's-macOS** is the single biggest fork in the decision tree for Apple's `container`; confirm the team's actual minimum-supported-macOS requirement before committing.
2. **Per-window resource cost** is the main scaling risk at 5–20 concurrent windows for *every* VM-per-window option (Docker Sandboxes, Apple `container`, Kata, E2B/microsandbox); none of the fetched docs publish hard memory/CPU numbers for N-way concurrency, so this needs to be benchmarked directly before committing, especially comparing "one full Docker Engine per sandbox" (Docker Sandboxes) against "one minimal VM, no nested engine" (Apple `container`, Firecracker-class tools).
3. **File-watching fidelity** favors no-VM options (bubblewrap, Seatbelt/`srt`) and penalizes 9p/reverse-sshfs-backed VM mounts (plain Lima, WSL2 cross-OS paths); virtiofs-backed options (Docker Sandboxes with caching on, Apple `container`, Lima ≥0.17 on VZ) are the best VM-class compromise, but none of the fetched docs make an explicit guarantee about recursive inotify propagation for an editor-grade watcher — this is worth a hands-on spike regardless of final pick.
4. **Network-policy-proxy + credential-broker** is a solved, documented feature only in **Docker Sandboxes** and **`gh-aw-firewall`** among the options surveyed; every VM-only runtime (Apple `container`, Kata, Firecracker/Cloud Hypervisor, Podman machine, Lima) would need this layer built by the team, for which `gh-aw-firewall`'s three-container (Squid + agent + API-proxy) pattern is the best open-source reference architecture found.
5. **Kata Containers' escape-CVE density** (§5) is a genuine red flag for a "security-focused fork" positioning; it should not be the default even though it is the most natural "VM-per-pod" Kubernetes-native choice for the cloud leg.
