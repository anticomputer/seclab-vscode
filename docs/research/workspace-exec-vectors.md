# VS Code Workspace-Trust / Code-Execution Attack-Surface Catalogue

**Scope note:** Everything under "Source-verified" was confirmed either by reading `microsoft/vscode` at pinned commit `6e35f5ceffa04ac728a0fb3a0dd6fb9cdb4ff100` (cloned/grepped directly in this session) or by fetching the primary GHSA/MSRC/vendor document. Items marked "Inference" are my architectural reasoning applied to verified facts, not independently confirmed in a lab. I did not execute any exploit code.

## 1. Architecture primitives that determine "where it runs"

**Source-verified**, `microsoft/vscode@6e35f5c`:

- Extensions declare/derive an **`extensionKind`**: `ui`, `workspace`, or `web`. An extension with a `main` (Node) entry point defaults to `workspace` kind (runs in the Remote Extension Host, REH) *unless* it declares `extensionKind:["ui"]`, in which case it is forced onto the **local** extension host even when the window is connected to a remote/REH — `microsoft/vscode:src/vs/workbench/services/extensions/common/extensionManifestPropertiesService.ts:411-445`. The user can override per-extension via the **user-level** (not workspace-level) setting `remote.extensionKind` — `...extensionManifestPropertiesService.ts:328-340`. Official doc: https://code.visualstudio.com/api/advanced-topics/extension-host ("`ui`… must run close to the UI… `workspace`… runs where the workspace is located").
  - **Verdict: this is the single most important residual surface.** Any extension (built-in or marketplace) that is `ui`-kind runs on the **local host**, not in the per-workspace sandbox, regardless of workspace content. This is extension-author-controlled, not workspace-attacker-controlled directly, but it means the fork cannot assume "REH = sandboxed, everything else is safe" — it must enumerate and specifically broker/restrict UI-kind extensions (auth providers, Settings Sync, Live Share, some debuggers/SCM UIs).
- Workspace-settings are gated by a **`restricted: true`** flag on each registered configuration key (`src/vs/platform/configuration/common/configurationRegistry.ts:230-233,874`). When a setting is `restricted`, its value from an **untrusted** workspace's `.vscode/settings.json` is dropped and only the user/machine value is honored. Verified restricted terminal settings include `Cwd`, `EnvMacOs/Linux/Windows`, `WindowsUseConptyDll`, `WindowsReparentConsoleWindow`, `AllowedLinkSchemes`, `EnableKittyKeyboardProtocol`, `EnableWin32InputMode`, `ShellIntegrationEnabled/DecorationsEnabled/Timeout/QuickFixEnabled`, `EnableImages`, `AllowInUntrustedWorkspace` — `src/vs/workbench/contrib/terminal/common/terminalConfiguration.ts:395-698`.
- Extensions instead declare **`capabilities.untrustedWorkspaces`** in `package.json`: `supported:true` (always enabled), `supported:false` (fully disabled until trust), or `supported:"limited"` with a `restrictedConfigurations` string-array naming the specific settings to ignore while untrusted. Doc: https://code.visualstudio.com/api/extension-guides/workspace-trust.
  - **Source-verified example — Git extension**: `capabilities.untrustedWorkspaces.supported:false` → the *entire* extension (status polling, submodule scan, auto-fetch) is disabled until the folder is trusted — `extensions/git/package.json:68-73`.
  - **Source-verified example — PHP extension**: uses the granular form, restricting only `php.validate.executablePath` — `extensions/php-language-features/package.json:24-51`. This is also the example the official docs use.
- `.vscode/tasks.json` **`runOn:"folderOpen"`**: gated twice — first by `IWorkspaceTrustManagementService.isWorkspaceTrusted()` (auto-tasks never collected/run while untrusted), then, even once trusted, by the `task.allowAutomaticTasks` prompt/setting (`on`/`off`/prompt) shown once per workspace storage key `task.hasPromptedForAutomaticTasks.v2` — `src/vs/workbench/contrib/tasks/browser/runAutomaticTasks.ts:47-54,170-199`. A second `runOn` value, **`worktreeCreated`**, now exists specifically to auto-run a task when an Agent-Session worktree is created — `src/vs/workbench/contrib/tasks/common/jsonSchema_v2.ts:385-388` — a new, less-reviewed automatic-execution trigger tied to the agentic/"Agents window" feature.

## 2. `.vscode/*` configuration-driven execution

| Vector | Trigger | Restricted-Mode gate | Execution location (remote setup) | Verdict (sandbox-by-default fork) |
|---|---|---|---|---|
| `tasks.json` any task run, incl. `runOn:folderOpen`/`worktreeCreated` | folder open / agent worktree create | Yes — blocked until trust + `allowAutomaticTasks` prompt (`runAutomaticTasks.ts:47-54`) | Task process spawned by the **task system**, which runs in whichever extension host owns the workspace folder — REH when remote | **Contained** if REH is sandboxed, *provided* the fork also sandboxes the new `worktreeCreated` trigger used by Agent sessions |
| `launch.json` / debug adapter launch | user starts debugging, or auto-attach | Yes — debugging fully disabled in Restricted Mode (doc: workspace-trust.md "Debugging") | Debug adapter process is spawned by the **debug extension**, which is `workspace`-kind by default → REH | **Contained**, *except* JS/Node debugger's historical node_modules-binary auto-resolution RCE (GHSA-f85p-3684-2g3j, below) which ran with the privileges of whatever process hosted the debugger — on desktop, that's local unless the debug extension itself was relocated to REH |

| `.vscode/extensions.json` recommendations | folder open (shows "install recommended extensions" notification) | Partially — recommending doesn't install, but a crafted file could produce an **error notification with a malicious clickable command-link that executed even in an untrusted workspace** | Local UI (notification rendering is always local) | **CVE: GHSA-xf67-g42g-pg73** (fixed 1.141.1, commit `fab0e01`) — a known Restricted-Mode bypass. **Host-side; fork must specifically sanitize/trust-gate notification command-links**, since notifications render on the local UI process regardless of REH sandboxing |
| `.gitattributes`-driven clean/smudge/merge filters, `diff.external`, `credential.helper`, `core.sshCommand`, `core.fsmonitor`, `core.hooksPath` in a repo's `.git/config` | any `git status`/`diff`/`fetch` invoked by the (trust-gated) Git extension, or by the user in a terminal | **Not gated by VS Code's Workspace Trust at all** — this is Git's own config-execution model, external to VS Code. Trusting the *workspace* in VS Code only re-enables the Git extension; it does not sanitize or override the repo's own `.git/config` | Git extension is `workspace`-kind by default → the `git` child process runs wherever the workspace folder lives → REH when remote | **Contained only if REH sandboxing also contains the spawned `git` subprocess and its FS/exec reach** — this is the general "GitSpawn" class of bug (Cloud Security Alliance research note, Sept 2026: https://labs.cloudsecurityalliance.org/research/csa-research-note-gitspawn-ai-coding-agent-rce-20260903-csa/, documenting that `core.fsmonitor` is read and the named helper executed by Git itself on any index-refreshing command such as `git status`/`git diff`, "outside whatever sandbox the agent otherwise enforces," and not gated by any confirmation prompt). Requires attacker control of the on-disk `.git` directory (e.g., an unzipped/archived repo, a malicious submodule, or restored `.git` metadata) rather than a plain `git clone`, since `clone` does not copy the remote's `.git/config`. Related, independently-confirmed VS Code bug: `GitHubCredentialProvider`'s unanchored `/github\.com/i` host regex let a `.gitmodules` entry pointing at `github.com.attacker.example` receive the signed-in GitHub token over Basic auth during `git submodule update`/recursive clone — **GHSA-qcxw-jfff-cxpc**, fixed 1.123.1, commit `4b6e246`, explicitly noted as *"not gated by workspace trust because credential delivery happens during the clone step."* |

## 3. Language-server / build-tool implicit execution

**Source-verified / documented:**
- **rust-analyzer**: `build.rs` execution and proc-macro expansion are both opt-in and explicitly coupled to project trust by the extension itself (`rust-analyzer.procMacro.enable`, `rust-analyzer.cargo.buildScripts.enable`; rust-analyzer will refuse/warn without workspace trust). Runs inside whichever host owns the rust-analyzer extension (workspace-kind → REH).
- **npm lifecycle scripts** (`postinstall` etc.) and **`package.json` dependency-name injection**: VS Code's own `package.json`-dependency hover/IntelliSense feature shelled out to the locally-installed `npm` to fetch metadata, and a maliciously named dependency could make `npm` run an arbitrary script — **GHSA-r6q2-478f-5gmr** (CVE-2023-36742), fixed in 1.82.1 (`e7b3397`) by disabling `npm` usage in untrusted workspaces and adding input validation. This is a **documented, patched, Workspace-Trust-relevant RCE** directly matching the "npm lifecycle" vector you flagged.
- **ESLint/Prettier/PostCSS config files are executable JS** (`.eslintrc.js`, `eslint.config.js`, `prettier.config.js`): these are loaded via Node `require`/`import` by the ESLint/Prettier **language-server extensions**, which are `workspace`-kind. Trail of Bits and multiple community write-ups treat "config-as-code" linter/formatter files as a standard code-execution-on-open vector; VS Code gates this only by disabling the whole extension in Restricted Mode (Workspace Trust doc, "Extensions" section) — once trusted, the config file's JS runs with the extension's full privileges.
- **TypeScript tsserver plugins** (`typescript.tsserver.pluginPaths`, workspace `tsconfig.json` `plugins`): loaded in-process into tsserver, a Node child process spawned by the (workspace-kind) TypeScript extension.
- **Python environment discovery** (`python.defaultInterpreterPath`, auto-detected venvs/conda envs, `pyproject.toml` build-backend invocation via `pip`/`build`): the Python extension resolves and later *executes* the configured interpreter for IntelliSense, testing, and debugging; a workspace-local virtualenv or `pyproject.toml` build-backend hook is effectively an executable path chosen by workspace content.
- **Jupyter kernels / `.ipynb`**: kernel selection launches an arbitrary (often workspace-local) Python/kernel executable; separately, notebook **outputs** (rendered HTML/JS) are a *distinct* code-execution surface — see §4.
- **`.envrc`/direnv**: not natively supported by VS Code; if the user's shell sources `.envrc` on `cd`, this is exactly the class of risk the official doc calls out under "Terminal" ("Shells can automatically execute code based on workspace contents, for example by sourcing `.env` files or running shell initialization scripts") — mitigated only by Restricted Mode blocking terminal creation at all, not by any direnv-specific control.
- **Gradle/Maven import**: the Java/Gradle extensions invoke the Gradle/Maven wrapper (`gradlew`/`mvnw`), which are themselves executable scripts checked into the repo; this is a long-standing, well-known "build-tool-as-code-execution" vector with no VS-Code-specific mitigation beyond disabling the Java extension pack in Restricted Mode.

**Verdict for all of §3**: these all execute inside whichever extension host owns the language/build extension — `workspace`-kind in the overwhelming majority of cases → **contained in the REH sandbox**, *provided* the fork's REH sandbox also constrains the child processes these tools spawn (npm, gradlew, pip/build backends, kernels), not just the extension host itself.

**Official webview security model** (https://code.visualstudio.com/api/extension-guides/webview#security): `enableScripts` gate, `localResourceRoots` allow-list (default = workspace root + extension folder), and an author-supplied `Content-Security-Policy` meta tag, all enforced inside an Electron `<iframe>`-equivalent sandboxed context, with VS Code's own "super-CSP" additionally constraining navigation/framing.

**Verdict**: Webview/notebook rendering happens in the **local UI renderer process** (it's a browser context hosted by the main window), even when the extension that created the webview is `workspace`-kind and runs remotely — the webview's *HTML/JS content* is fetched from the REH but *executes locally in the Electron renderer*. This is **not automatically contained by an REH sandbox** — it is a structurally local execution surface (same conclusion as the official extension-host table: "local" and "web" extension hosts both run "on the same machine as the user interface"). **The fork must treat the webview/notebook-output renderer as part of the local-host attack surface it needs to isolate (e.g., via its own OS-level sandboxing of the renderer, or routing webview content load through the per-workspace credential/network broker), not assume the REH sandbox covers it.**

SVG rendering in the editor/preview and Markdown preview (`markdown.preview.*`, CSP-restricted iframe) follow the same local-webview model and were historically a prolific source of CVEs (the whole "webview sandbox escape" line above).

## 5. Dev Containers, `.vscode/mcp.json`, `extensions.json`

### Dev Containers — **host-side by design**
- Official spec/doc (https://containers.dev/implementors/spec/#initializecommand, https://code.visualstudio.com/docs/devcontainers/create-dev-container): `initializeCommand` runs **on the host**, before the container exists, with the full privileges of the user running VS Code — "runs locally before anything else." It is explicitly *not* sandboxed and is treated "as trusted as any other user-run script" per community guidance (a Ken Muse blog post on `initializeCommand`, since removed from kenmuse.com; the spec links above are the primary sources).
- `postCreateCommand`/`postStartCommand`/`postAttachCommand` run **inside** the container but frequently as root (default container user), and — per the Trail-of-Bits-adjacent community write-up "Exploiting Visual Studio Code Devcontainers" (https://dev.to/jamiemccrindle/exploiting-visual-studio-code-devcontainers-16fb) — are a standard vector for credential exfiltration (`postAttachCommand` tar-and-curl of the mounted workspace, including `.env`/`.npmrc`), and "docker-from-docker" (mounting `/var/run/docker.sock` into the devcontainer) gives the container **unfettered host access**, defeating any container-boundary isolation entirely.
- **Dev Container Features** (`ghcr.io/devcontainers/features/*`) execute arbitrary `install.sh` scripts, typically as root, during image build — a third-party supply-chain surface distinct from the base image.

**Verdict: `initializeCommand` is unambiguously host-side and is explicitly called out by the user's own framing as a residual surface** — the fork must route it through the sandbox/broker (e.g., execute it *inside* the workspace sandbox rather than on the bare host, or require separate, explicit approval scoped outside the window's blast radius) since upstream VS Code does not gate it by Workspace Trust at all beyond the general "do you trust this repo" folder-open prompt. `postCreateCommand`/Features are **inside the container** already, so they are naturally contained by a per-workspace sandbox *unless* the devcontainer config itself requests a docker-socket bind-mount or privileged mode, which must be specifically disallowed/brokered by the fork.

### `.vscode/mcp.json` / `.mcp.json`
- **Source-verified**: a workspace-root `.mcp.json` (`WorkspaceDotMcpDiscovery`) is registered with `trustBehavior: McpServerTrust.Kind.Trusted` and carries `remoteAuthority: this._remoteAgentService.getConnection()?.remoteAuthority`, i.e. the server definition is associated with the **remote** connection when one exists — `src/vs/workbench/contrib/mcp/common/discovery/workspaceDotMcpDiscovery.ts:62-68`. This indicates stdio MCP servers defined in workspace config are intended to spawn in the remote/workspace context, not on the local UI host.
- VS Code already ships a native, non-trivial **MCP sandboxing subsystem** (`mcpSandboxService.ts`, 466 lines) with per-server allow-listed network/filesystem-write permissions, OS-sandbox integration (`srtPath`/sandbox temp dir), and explicit sandbox-config-suggestion UI — `src/vs/workbench/contrib/mcp/common/mcpSandboxService.ts:1-80`.
- **But this sandbox had its own escape**: **GHSA-qghm-w43w-vx8v** (CVE-2026-102851) — approved network/filesystem-write permissions were saved to **shared** sandbox config rather than scoped per-server, so an attacker-controlled MCP server sharing a config with a previously-approved server inherited that server's grants without a separate prompt. Fixed 1.141.1, commit `34329e2`.
- Related MCP-specific CVEs: **GHSA-g6p5-6xp8-5jwg** (CVE-2026-81377) — gallery/registry metadata path-traversal let install/update of a malicious MCP server overwrite files **outside** its storage dir, or trigger recursive deletion outside the MCP dir on uninstall (fixed 1.136.2, `6a88486`); **GHSA-9f6c-63gp-pwpf** (CVE-2026-41613) — MCP deep-link install omitted disclosure of env vars/headers being granted (fixed 1.119.1, `be09b4c`); **GHSA-6xq8-9qf3-p6qv** (CVE-2026-21518) — workspace trust was not always demanded before starting MCP servers at all (fixed 1.109.1).
- **Verdict**: MCP stdio servers are architecturally intended to run where the workspace runs (REH when remote) and VS Code is independently building sandbox isolation for them — this is **the closest existing upstream analogue to your proposed per-workspace sandbox design**, and its CVE history (shared-permission leakage, trust-demand gaps, path traversal) is a direct source of lessons for the fork's own credential/permission broker (don't let one workspace's approved grants apply to another MCP server or workspace).

### `.vscode/extensions.json`
Covered in §2 — **GHSA-xf67-g42g-pg73**, a local, host-rendered notification-link RCE bypassing Restricted Mode entirely.

## 6. URI handlers, `code` CLI, "Open in VS Code" links, Settings Sync

**Source-verified CVEs**, all `microsoft/vscode`:

- **GHSA-jfjw-mv65-hg44** (CVE-2022-30129): `vscode://` **git-clone-from-URL** handler executed commands locally from an unvalidated URL once the user confirmed the open-URL prompt. Fixed 1.67.1, `c5da533`. *(This is the canonical "Open in VS Code" deep-link RCE and precisely matches the user's named vector.)*
- **GHSA-5j3g-c7qg-xfvx** (CVE-2026-47281): a crafted **`.code-workspace` file** with a direct `host:port` remote authority silently connected the extension-host backend to an **attacker-controlled server with no confirmation**. Fixed 1.123.1, `9505d0f`.
- **GHSA-2cmq-rv52-5rf6** (CVE-2026-78462): remote-agent-host addresses and local-file permission grants could be read from an untrusted repo's `.vscode/settings.json`, letting a crafted repo silently redirect the window's remote-agent connection and grant it local-file access — "the user does not need to trust the workspace." Fixed 1.136.2, `4321a67` (now sourced only from global config, marked `restricted`).
- **GHSA-r2p5-jgfw-r5vw** (CVE-2026-70098): opening a workspace via `vscode.dev/agents/tunnel` **skipped Workspace Trust entirely**, letting attacker-contributed "skills" run with no warning. Fixed 1.141.1, `010ee1a`.
- **GHSA-36qf-jgq9-4m6j** (CVE-2026-59113): the **Fetch Web Page** chat tool's hidden web-content loader could launch **OS protocol handlers** (i.e., arbitrary `xxx://` URI schemes, including custom-registered local-app handlers) without an extra prompt, and extension URL-overrides could run before URI-trust approval. Fixed 1.132.1, `89e1c70`.
- **GHSA-5cm6-54wm-6gg6** (CVE-2023-39956): `code <attacker-controlled-workspace>` from the **CLI**, with an attacker-writable working directory, led to local command execution via an underlying Electron bug. Fixed 1.80.2 (Electron bump).
- **GHSA-v282-cxqj-xgj4** (CVE-2026-57102) / **GHSA-54p6-6j68-j5vr** (CVE-2024-26165) / **GHSA-532g-4pv9-25f2** (CVE-2025-24039): three separate `code serve-web` / remote-server CLI issues — connection-token retrievable by domain-knowledge attacker, connection token visible via process-argument inspection by lower-privileged local users, and Windows DLL-planting in world-writable dirs (`C:\node_modules`) hijacking the remote server's Node module resolution.
- **GHSA-fp6w-v29h-43rj** / **GHSA-h29r-p8vr-4vfm** (CVE-2026-70336 / CVE-2026-69320): VS Code **web** URL could carry a privileged payload (including **`NODE_OPTIONS`/`--import`**) into the remote extension-host/terminal bootstrap, so the *next* Node command the victim ran in the terminal executed attacker code ("fileless RCE via URL-controlled NODE_OPTIONS").

**Settings Sync**: no VS Code-specific CVE found in the advisory pages reviewed, but it is a documented, structural supply-chain amplifier — Settings Sync auto-installs the same extension set (and settings, including `extensions.supportUntrustedWorkspaces` overrides) on every machine linked to the account; a single compromised or auto-updated malicious extension propagates everywhere Sync is enabled (official doc: https://code.visualstudio.com/docs/configure/extensions/extension-runtime-security, "the extension host has the same permissions as VS Code itself"; community/industry coverage: Ken Muse "Pinning VS Code Extensions to Fight Supply Chain Attacks," Checkmarx "How we take down malicious Visual Studio Code extensions," Cloud Security Alliance "VSCode Marketplace Poisoning" research note).

**Verdict**: Every item in this section executes on, or reconfigures, the **local UI/CLI host process** — the URL/URI handler, the `code` CLI, and Settings Sync's extension installer are all local-host components by construction (they run before, or independently of, any REH connection). **This is explicitly the "residual host-side surface" class the user's design brief calls out** — a per-workspace REH sandbox does nothing for any of these; they need their own brokering (e.g., URI-handler and CLI actions get a confirmation/allow-list step mediated by the host sidecar, and Settings Sync's extension-install path is treated identically to a fresh marketplace install, subject to the same per-workspace trust/kind rules).

## 7. Symlink / path-traversal escapes from a mounted workspace

**Source-verified pattern** (recurring root cause across multiple 2026 CVEs above): VS Code's path-containment checks for `localResourceRoots`, remote workspace-trust folder inheritance, and profile-snippet import all shared a single bug class — **inconsistent path-separator semantics between the containment check and the actual resource resolution** for non-`file`-scheme URIs (e.g. `vscode-remote`), where backslashes were treated as literal filename characters by the check but as path separators by the resolving file-system provider. This allowed a crafted path to pass the "is this inside the allowed root" check yet resolve **outside** it. See GHSA-pc77-xwc5-p6jp, GHSA-x5qc-gqm7-93qp, GHSA-89cr-6h4p-hpx9 (full details in §4/§6). All fixed by normalizing both the candidate and parent path under both POSIX and Windows semantics before comparing (commits `e28ec75`, `461bd99`, `b0240f4`).
- **Profile-snippet Zip-Slip**: **GHSA-hgwg-xqr5-q87f** (CVE-2026-47287) — importing a crafted `.code-profile` with a path-traversal snippet *name* (e.g. containing `../`) wrote attacker content **outside** the profile snippets directory, to any user-writable location — a classic zip-slip-style escape via a VS-Code-specific mechanism, not the OS filesystem mount itself. Fixed 1.123.1, `9b31ff8`.
- **Inference (not independently verified in this session)**: `files.followSymlinks` defaults to `true` in VS Code's file-explorer/search, meaning a symlink committed inside the workspace that points outside the workspace root (e.g., to `/etc`, `~/.ssh`, or a sibling mounted workspace) will generally be followed by editor/search/file-watcher operations unless the *sandbox mount itself* (bind-mount namespace, container FS) prevents the link target from resolving to anything outside the mount. **For the fork, this means the symlink-escape risk must be closed at the mount/container boundary (host-side mount namespacing), not relied upon to be caught by VS Code's own path-containment logic, which — per the CVEs above — has repeatedly had exploitable gaps.**

## 8. Chat/Agent-specific execution & credential-exfiltration CVEs (2025–2026, directly relevant to "rogue extension/agent blast radius")

These are newer than the classic Workspace-Trust literature but squarely match "other such code exec abused from the workspace trust boundary," since several explicitly bypass or never reach a trust/approval boundary:

- **GHSA-fq62-m6f5-c7h9** (CVE-2026-102232): Copilot agent harness auto-approved edits to enabled custom **hook** / **agent-definition** files (`chat.hookFilesLocations`/`chat.agentFilesLocations`), letting prompt injection plant a shell command that later executes with full user privileges when the hook fires. Fixed 1.141.1 (commits `fffc9bc`, `a5af62a`).
- **GHSA-w79w-rj9h-vg4f** (CVE-2026-70335) and **GHSA-rg3f-8xq5-hwh6** (CVE-2026-41109): earlier instances of the same class — prompt injection writing custom-agent hook files, and GPT-family `apply_patch` bypassing the "sensitive file" approval mechanism. Fixed 1.132.1 / 1.119.1.
- **GHSA-m8rw-hr26-pw53** / **GHSA-rvgr-2w56-2j67** (CVE-2026-102231 / CVE-2026-81381): a workspace-overridable Azure DevOps Code-Search endpoint setting (`github.copilot.chat.workspace.prototypeAdoCodeSearchEndpointOverride`) let a malicious workspace redirect Copilot's ADO Code Search requests — **including the user's ADO access token, sent via Basic auth** — to an attacker server. Fixed 1.136.2.
- **GHSA-wr9x-42j2-jvh3** (CVE-2026-47282): hidden "advanced" Copilot settings honored from an **untrusted** workspace's settings.json could redirect the (short-lived, 30-minute) Copilot token to a malicious upstream. Fixed 1.128.1, `f05bcd1` (now only honored in trusted workspaces).
- **GHSA-vww8-mqc2-4x8v** (CVE-2026-81380): agent-generated Markdown with a remote-source image could exfiltrate workspace data encoded in the image URL **before** chat's remote-image block-policy ran (DOM already materialized the request). Fixed 1.136.2, `88e44fa`.
- **GHSA-6xp2-9cj3-f488** / **GHSA-hr37-8jwr-q8p8** (CVE-2026-69306 and related "Agent Network Filter Bypass"): the agent network egress filter's URL-authority matcher mishandled IPv4-mapped IPv6 literals / bracketed IPv6, letting Fetch-Page/Browser tools reach **local HTTP services** despite a deny-all/allowlist network policy. Fixed 1.132.1, `0c5eba4`.
- **GHSA-3hjg-cwxj-qfc6** (CVE-2026-65675): Claude agent integration's "Edit automatically" permission mode let the agent edit files **outside the workspace** entirely (not scoped to the granted workspace), exploitable via prompt injection. Fixed 1.132.1, `8af0773`.

**Why this matters for the fork**: these are precisely "rogue agent/extension blast radius" bugs, and several (network-filter bypass reaching `localhost`, token exfiltration via workspace-overridable endpoints, hook auto-approval) demonstrate that **Microsoft's own in-process mitigations (network allow-lists, "sensitive file" approval, per-session token scoping) have repeatedly had gaps**. This is a strong architectural argument *for* your design: a host-side credential broker that never hands the sandboxed REH a long-lived, directly-usable token, and a host-side (not REH-internal) egress proxy enforcing network policy, would close whole classes of these bugs by construction rather than by per-feature patching.

## 10. Residual host-side execution surfaces the fork must specifically close or route into the sandbox

1. **`devcontainer.json` `initializeCommand`** — runs on the bare host before any container/sandbox exists, by spec; not gated by Workspace Trust.
2. **Docker-socket / privileged-mode escape hatches in `devcontainer.json`** (`mounts`, `runArgs: --privileged`) — these let an in-sandbox container regain full host access; must be disallowed or brokered.
3. **Local ("UI"-kind) extensions** — `extensionKind:["ui"]` forces local-host execution regardless of workspace trust; requires an explicit inventory/allow-list and its own confinement (it cannot simply inherit "REH is sandboxed, done").
4. **Webview/notebook/Markdown-preview rendering** — executes in the local Electron renderer even for remote-owned extensions; `localResourceRoots`/CSP containment has a multi-year history of bypasses (Trail of Bits 2023; six+ 2026 GHSAs on path-separator confusion alone).
5. **`vscode://` URI handler and "Open in VS Code" deep links** — local-host command execution gated only by a user-confirmation dialog that has itself been bypassed (GHSA-jfjw-mv65-hg44; Fetch-Web-Page OS-protocol-handler bypass GHSA-36qf-jgq9-4m6j).
6. **The local `code` CLI, including `code serve-web`/tunnels** — connection-token leakage via process args or domain guessing; `NODE_OPTIONS`/bootstrap-variable injection from URL payloads reaching local or remote terminal/extension-host startup.
7. **Settings Sync's extension/settings installer** — a pre-workspace, host-level propagation channel that must be treated as equivalent to an untrusted fresh install, not as implicitly trusted "your own" configuration.
8. **Host-side notification/command-link rendering** — the error-notification-with-command-URI bypass (GHSA-xf67-g42g-pg73) shows that even "just showing a dialog" is host-side code-execution-adjacent and needs trust-aware sanitization independent of REH sandboxing.
9. **The credential-brokering boundary itself** — several 2025–2026 CVEs (ADO token to attacker endpoint, Copilot token exfiltration, GitHub Basic-auth token to a look-alike host, shared MCP sandbox permission leakage) show that *whatever* component hands out credentials needs per-destination/per-server scoping with no shared/implicit trust — directly informs the design of the proposed host-side credential sidecar.
