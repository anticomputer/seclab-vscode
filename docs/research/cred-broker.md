## 1. Credential-injecting proxies

### Docker Sandboxes (host proxy)
**How it works:** Each sandbox is a microVM; all outbound TCP is forced through a host-resident proxy. The agent only ever sees a *sentinel* value (literally the string `proxy-managed` for API keys); the host-side proxy matches the outbound request against a kit-declared service definition, decides the header to write, and injects the real value "looked up on the host." The real credential never crosses into the VM.
- Architecture & "follow an authenticated request" walkthrough: https://docs.docker.com/ai/sandboxes/architecture/
- Credential mechanics (sentinel masking, OAuth passthrough opt-out, stored/custom secrets, OS keychain backing): https://docs.docker.com/ai/sandboxes/configuration/credentials/
- Security model / trust boundaries: https://docs.docker.com/ai/sandboxes/security/ and isolation layers: https://docs.docker.com/ai/sandboxes/security/isolation/
- Default-deny network posture, `sbx policy ls`: https://docs.docker.com/ai/sandboxes/security/defaults/

**Policy runtime-mutability (verified):** `sbx policy allow/deny network [--sandbox X] [--method M] [--path P] [--query Q]` changes "take effect immediately," with per-sandbox or fleet-wide scope, and HTTP method/path/query-level granularity (not just host-level) — this is the most expressive allow-list schema of everything surveyed: https://docs.docker.com/ai/governance/local/network-rules/

**TLS interception requirement — gap:** Docker's docs describe the result ("sees only a sentinel… real value never enters the sandbox") but do **not** explicitly publish whether this is implemented via CA-based MITM of the sandbox's outbound HTTPS or via a tokenizer-style "client speaks plaintext HTTP, proxy upgrades to HTTPS" pattern. **[inference]** Given it injects into "outbound HTTP headers" for an ordinary HTTPS API call, some form of TLS termination at the proxy is required; the mechanism isn't documented in detail in the pages fetched. Flagged as unverified.

**License/maturity:** `sbx` itself is Docker's own CLI/product (free for local use, paid for governance/cloud), not an independently licensed OSS library you can vendor. The open part is `docker/sandbox-kit-spec` (Apache-2.0, created Sept 2026, 175★, actively pushed) — the *interface* kits use to declare credential bindings (`credential@1.md`), not the proxy implementation: https://github.com/docker/sandbox-kit-spec/blob/main/docs/spec/capabilities/com.docker.sandbox/credential@1.md
**Embeddability:** Not directly embeddable as a library into a third-party desktop app; you'd either shell out to `sbx` as a sandbox-runtime dependency, or treat its documented architecture as a design template to reimplement.

### fly.io tokenizer (`superfly/tokenizer`)
**How it works:** An HTTP proxy. The client encrypts ("seals," via NaCl `Sealed Box`) a secret description — the real token, an optional destination header/query name (`dst`), a `printf`-style format (`fmt`), and the auth required of the caller — with the proxy's public key. The client sends the sealed blob in a `Proxy-Tokenizer` header on a **plaintext HTTP** request; the proxy decrypts, injects the real secret into the specified header/query, and **transparently upgrades the connection to HTTPS** to the real upstream. https://github.com/superfly/tokenizer (README)
- `inject_processor` (header or `query:<param>` destination, format string), `inject_hmac_processor` (HMAC-signs the request body or a custom message), and a **`sigv4_processor`** that re-signs AWS SigV4-style requests from a sealed AWS key without the caller ever holding it — directly relevant to cloud-CLI brokering (§2): same README.
- Anti-replay: the sealed secret can embed a `bearer_auth.digest` so the proxy also requires the *caller* to present a matching bearer secret before it will honor the sealed token — i.e., knowledge of the opaque `Proxy-Tokenizer` blob alone isn't sufficient (relevant to §5 replay pitfall): same README, "Example" section.
- Fly's own deployment docs: https://github.com/superfly/tokenizer/blob/main/docs/FlyTokenizer.md

**TLS:** No client-side CA trust is needed — the model deliberately avoids MITM by having the client speak **plaintext HTTP to the proxy** (requiring the client↔proxy hop to be secured by other means, e.g. a VPN/private network, per the README's explicit warning) and TLS is only re-established proxy→upstream.
**Runtime mutability:** Policy is baked into each sealed secret at mint time (host/dst/fmt/auth are all part of the encrypted payload); there's no separate live policy API in what I read — mutability happens by minting a new sealed secret, not by editing a central rule store. **[inference, moderate confidence — I did not find a revocation/registry API in the docs read]**
**License/maturity:** Apache-2.0, 504★, pushed 2026-10-30 (active). Small, single-purpose Go-ish HTTP proxy — straightforward to run as a host-managed sidecar process.

### Envoy `credential_injector` HTTP filter
**How it works:** An HTTP filter (`envoy.filters.http.credential_injector`) that injects a credential into the outgoing `Authorization` header (Basic or Bearer) of proxied requests. Two built-in credential sources: `generic` (static secret) and `oauth2` (client-credentials grant; Envoy fetches/refreshes the token itself from a configured token endpoint). Explicitly scoped to **workload identity**, not end-user auth — "the identity associated with the inserted credential is considered the identity of the workload behind the Envoy proxy": https://www.envoyproxy.io/docs/envoy/latest/configuration/http/http_filters/credential_injector_filter
Source: https://github.com/envoyproxy/envoy/tree/main/source/extensions/filters/http/credential_injector (filter) and https://github.com/envoyproxy/envoy/tree/main/source/extensions/http/injected_credentials (generic/oauth2/common sub-extensions), confirmed present at HEAD `ac6efa8` (2026-11-04).

**TLS:** Not addressed by the filter doc itself — this filter only rewrites headers on requests Envoy already sees in cleartext (post-TLS-termination). In the common Envoy/Istio sidecar pattern, outbound app traffic is redirected to the local sidecar via `iptables`/namespace routing as the next hop; if the app itself originates TLS to the real upstream, Envoy must either (a) terminate client TLS as a true forward proxy (requiring a CA trusted by the sandboxed client, same requirement as mitmproxy/Squid-SSL-bump) or (b) have the app configured to speak plaintext to the local sidecar and let Envoy originate the outbound TLS — architecture-dependent, not specified by the filter doc. **[inference]**
**Runtime mutability:** Envoy's xDS/ECDS (Extension Config Discovery Service) generally allows HTTP filter configuration to be pushed by a management server and applied to new connections without a restart: https://github.com/envoyproxy/envoy/blob/main/api/envoy/service/extension/v3/config_discovery.proto . I did not find an explicit worked example of `credential_injector` wired through ECDS specifically — general capability confirmed, specific usage **[inference]**.
**License/maturity:** Apache-2.0, 29,179★, CNCF-graduated, extremely mature, Envoy ships daily.
**Embeddability:** Heaviest option of those surveyed — a full static C++ binary with YAML/xDS config. Feasible to run as a per-workspace sidecar process controlled by a tiny local xDS management server written by the editor's host process, but much more integration surface than Tokenizer, smokescreen, or mitmproxy for a first prototype.

### mitmproxy
**How it works:** Python-scriptable MITM proxy; a `request`/`response` addon hook can rewrite headers/bodies arbitrarily (demonstrated pattern: strip real auth, inject a different credential, as shown in the project's own addon examples: https://docs.mitmproxy.org/stable/addons/examples/ and https://github.com/mitmproxy/mitmproxy/blob/main/docs/src/content/addons/overview.md).
**Proxy modes relevant to the "proxy-unaware clients" pitfall:** Regular (explicit `HTTP_PROXY`), **Local Capture** (OS-level eBPF/pf transparent capture by process name/PID, *no client proxy-awareness required*, root required on Linux to load the BPF program, supported on Windows/Linux/macOS, Linux kernel ≥6.8), Reverse, WireGuard (external devices), Transparent, TUN, Upstream-chaining, SOCKS, DNS: https://docs.mitmproxy.org/stable/concepts/modes/ — note the explicit caveat: "Capturing traffic from containers will fail unless they use the host network," directly relevant to a container-based sandbox.
**TLS:** Requires the mitmproxy CA to be trusted by the client. Unique per-install (generated on first run, not shared across installs), with a `mitm.it` self-install webapp plus documented manual-install steps per platform (curl `--cacert`, macOS Keychain, Java `keytool`, Android, iOS "Enable full trust for root certificates," etc.): https://docs.mitmproxy.org/stable/concepts/certificates/
**Runtime mutability:** Fully live — addons are Python objects with in-memory state; nothing stops you from exposing a local control channel (gRPC/HTTP/IPC) that an addon reads to update per-request policy instantly, since mitmproxy is driven by its own Python event loop, not static config files.
**License/maturity:** MIT, 46,634★, very actively maintained (pushed within hours of research) — the single most mature, best-documented, most protocol-complete (HTTP/2, WebSockets — see §5) option surveyed, and it is importable as a Python library (`mitmproxy.addons`, `mitmproxy.proxy`), not just a CLI, making host-process embedding straightforward.

### Deno Sandbox secrets
**How it works:** At sandbox-creation time you declare `secrets: { NAME: { hosts: [...], value } }`. Inside the VM, the env var holds the **literal string** `<placeholder>` — not a derivable token. Deno Deploy's infrastructure substitutes the real value **only at the network layer**, only for outbound requests to a host in that secret's `hosts` list, and only if that host is *also* present in the separate `allowNet` egress allowlist (both must match independently — defense in depth): https://docs.deno.com/sandbox/security/
**Design relevance:** This is the cleanest documented example of "credential bound to specific host(s), substituted only on egress to approved hosts, placeholder otherwise" — directly matching the brief's ask.
**Caveat:** Deno Sandbox is Deno Deploy's **hosted, multi-tenant SaaS microVM product** — the substitution engine is proprietary infra, not an open-source local proxy you can run yourself. It is valuable here purely as a **validated design pattern**, not as off-the-shelf embeddable code.
**Granularity gap vs. Docker Sandboxes:** host-level only in the docs read (`example.com`, `*.example.com`, `host:port`, exact IPs) — no path/method/query scoping documented, unlike Docker Sandboxes' `--method`/`--path`/`--query`.

### Stripe `smokescreen`
README-level description: an HTTP **CONNECT** proxy that enforces a hostname allow-list ACL plus DNS-resolution checks (rejects requests that resolve to private/CGNAT/non-global-unicast IPs — SSRF protection), client-identified via mTLS certificate CN, with per-client ACLs: https://raw.githubusercontent.com/stripe/smokescreen/master/README.md

**Code-verified finding beyond the README — smokescreen also does credential injection:** Reading `pkg/smokescreen/acl/v1/acl.go` and `pkg/smokescreen/smokescreen.go` at commit `5b4b7aabca9bc70a8435358d648edd03294c299e` shows each ACL `Rule` can declare `MitmDomains []MitmDomain{AddHeaders map[string]string, DetailedHttpLogs bool, ...}` (acl.go:49-61). At connect-time, if a rule's `MitmConfig` is set and the server is configured with a MITM CA (`Config.MitmTLSConfig func(host, ctx)(*tls.Config, error)`, config.go:176-177), smokescreen performs a per-domain MITM `CONNECT` and injects the declared headers via a `MitmMutateRequest` callback before forwarding (smokescreen.go:1010-1033):
```go
if sctx.Decision.MitmConfig != nil {
    if config.MitmTLSConfig == nil { /* deny: MITM not enabled */ }
    mitm := sctx.Decision.MitmConfig
    if len(mitm.AddHeaders) > 0 {
        mitmMutateRequest = func(req *http.Request, ctx *goproxy.ProxyCtx) {
            for k, v := range mitm.AddHeaders { req.Header.Set(k, v) }
        }
    }
    connectAction = &goproxy.ConnectAction{Action: goproxy.ConnectMitm, TLSConfig: config.MitmTLSConfig, MitmMutateRequest: mitmMutateRequest}
}
```
Source: https://github.com/stripe/smokescreen/blob/5b4b7aabca9bc70a8435358d648edd03294c299e/pkg/smokescreen/smokescreen.go#L1010-L1033 and https://github.com/stripe/smokescreen/blob/5b4b7aabca9bc70a8435358d648edd03294c299e/pkg/smokescreen/acl/v1/acl.go#L49-L66

This means smokescreen is **both** an allow-list/SSRF proxy *and*, when its MITM CA is configured, a credential injector — requiring the same client-CA-trust precondition as mitmproxy. This capability is undocumented in the README/CLI help and only visible in source — worth flagging since it changes smokescreen's fit for this project materially.

**Runtime mutability:** ACL is loaded via a `Loader` interface from an `--egress-acl-file`; live-reload requires either a file-watching `Loader` implementation or a restart — not natively a push API. **[inference from code structure]**
**License/maturity:** MIT, 1,389★, created 2016, pushed same day as this research (very actively maintained, production-proven at Stripe).
**Embeddability:** A Go module (`pkg/smokescreen`) importable directly into a Go host process, or runnable as its own binary — good fit if the broker's host process is Go.

### GitHub `gh-aw-firewall` (+ gh-aw MCP gateway, safe-outputs)
**How it works:** `awf` wraps a command in three containers: a **Squid** proxy enforcing a domain allow-list, the **agent** container (all HTTP/HTTPS routed through Squid), and an "always enabled" **API proxy sidecar** that "holds LLM API keys so they never reach the agent process" — this is the closest literal off-the-shelf match to "credential sidecar" in the brief: https://github.com/github/gh-aw-firewall (README)
- `--enable-api-proxy`: Node.js proxy sidecar injecting keys for Copilot/OpenAI/Anthropic/Gemini/Vertex, with per-provider rate limits and Anthropic prompt-cache rewriting; `--ssl-bump` + `--allow-urls` for HTTPS URL-path-level filtering (standard Squid SSL-bump, implying a CA trusted inside the agent container); `--difc-proxy-ca-cert <path>` explicitly documents "Path to TLS CA cert written by external DIFC proxy" when chaining to an external multi-cloud proxy gateway; `--dns-servers` restricts DNS resolution to trusted servers and `--dns-over-https` hardens it further; `--enable-dlp` does outbound DLP scanning "to block credential exfiltration in outbound request URLs": https://github.com/github/gh-aw-firewall/blob/main/docs/usage.md
**Compatibility constraint (important for a desktop app):** Linux + Docker only — macOS/Windows GitHub-hosted runners are explicitly unsupported because they're themselves non-nested-virtualization VMs ("Virtualization is not available on this hardware"): https://github.com/github/gh-aw-firewall/blob/main/docs/compatibility.md . If the VS Code fork's sandbox runtime is Linux-based (microVM/container), this is directly reusable; if it must also run natively sandboxed on macOS/Windows hosts, `awf` as shipped won't run there as-is.
**License/maturity:** MIT, 157★, created Oct 2025 — young, but official and under active daily development.

**gh-aw MCP Gateway** (draft spec v1.18.0): "a transparent proxy service that enables unified HTTP access to multiple MCP servers," requiring stdio MCP servers to be containerized (no bare `command` execution, specifically for isolation/portability), config delivered over **stdin** (keeps secrets out of process argv), per-server `headers` (commonly used for upstream auth), per-server `caCertFile` (custom trusted CA per upstream), and an optional `auth` object for upstream OIDC: https://github.github.com/gh-aw/reference/mcp-gateway/

**Safe-outputs**: complementary pattern — rather than granting the agent job write tokens, the agent emits structured output calls (`create_issue`, etc.) that a *separate, permission-scoped job* validates and executes, so "a read-only `GITHUB_TOKEN` does not remove other credentials" is an explicit documented caveat authors must still manage: https://github.github.com/gh-aw/reference/safe-outputs/

**Three-layer trust architecture** (this is the best direct answer to the brief's reference to "what GitHub is developing for Actions"): substrate-level trust (runner/microVM/firewall/API-proxy/MCP-gateway), configuration-level trust (declarative workflow/firewall/MCP config as "imported capabilities that bound components' external effects"), and agent-level trust: https://github.github.com/gh-aw/introduction/architecture/

## 2. Non-HTTP credentials

### SSH
- **Built-in OpenSSH mechanism, zero extra component:** `ssh-add -c <key>` marks a key "confirm," so the agent triggers an interactive OS prompt (ssh-askpass) on every signing operation before using that key — this is the simplest possible per-use confirmation primitive and ships in stock OpenSSH: https://man.openbsd.org/ssh-add (`-c` flag, "Indicates that added identities should be subject to confirmation").
- **GitHub's own guidance warns against blanket forwarding:** "Never use agent forwarding... for `Host *`" and to scope `ForwardAgent yes` per trusted host: https://docs.github.com/en/authentication/connecting-to-github-with-ssh/using-ssh-agent-forwarding
- **Dedicated filtering-proxy projects exist but maturity is weak.** `tiwe-de/ssh-agent-filter` ("filtering proxy for ssh-agent meant to be forwarded to untrusted servers") is **archived since 2016/2026-12 last push, no license file, 50★** — i.e., exactly the component you'd want, but effectively unmaintained/unlicensed, a real risk if reused as-is. Alternatives from a live GitHub search: `krisiasty/ssh-agent-proxy` ("filter SSH agent keys into per-socket groups," Apache-2.0, pushed 2026-11-02, but only 4★) and `jnoxon/ssh-agent-utils` ("multiplex and filter SSH agents," MIT, 4★, last pushed 2023). None of these are production-proven at scale. (Repo metadata captured directly via `gh api`.)
- **Protocol basis for a custom build:** the SSH agent protocol is simple and documented in IETF draft `draft-miller-ssh-agent` (expired draft but the de facto spec OpenSSH implements) — request/response messages like `SSH_AGENTC_SIGN_REQUEST`/`SSH_AGENT_SIGN_RESPONSE` over a Unix domain socket: https://www.ietf.org/archive/id/draft-miller-ssh-agent-14.html . A purpose-built broker can terminate `$SSH_AUTH_SOCK` inside the sandbox, forward only approved `SIGN_REQUEST`s (matched by key fingerprint, and the destination host if determinable from the SSH client's banner/handshake) to the real host-side agent, and raise the editor's trust-prompt UI for new key/host combos — this is a modest, well-scoped protocol to implement from scratch given the unmaintained state of existing filters.
- **Production reference for the UX pattern (not a filtering proxy per se):** Bitwarden's SSH agent implements per-connection/per-key approval prompts as a maintained, shipping product: https://bitwarden.com/help/ssh-agent/

### Git over HTTPS
- git's credential-helper protocol (`git credential fill/approve/reject`, `credential.helper` config) lets any external program act as the credential source and is fully documented: https://git-scm.com/docs/gitcredentials . A surrogate helper returns a fixed sentinel (e.g., username `x-access-token`, password `SURROGATE-<id>`), and the egress proxy (same engine as §1) swaps it for the real token on the way to `github.com`/`api.github.com`. GitHub's own `gh auth git-credential` is a working example of a CLI-managed credential helper that itself could be adapted to return sentinels: documented via `gh auth login`/`git config --global credential.helper "!gh auth git-credential"` usage.
- Simpler alternative that needs no credential-helper changes at all: since `git`'s HTTPS transport is just another proxy-aware HTTPS client, routing it through the same sandbox-wide MITM proxy (with the per-sandbox CA already trusted for §1) lets the proxy inject the real `Authorization` header directly, exactly like any other HTTPS API call — no git-specific plumbing required. **[inference, architecturally straightforward given the rest of the design]**

### Cloud CLIs
- **AWS — `credential_process`:** a profile setting in `~/.aws/config` that has the SDK/CLI spawn an external program and read JSON credentials from its stdout; explicitly documented as the extension point "for custom implementations, such as retrieving credentials from an on-premises credentials store": https://docs.aws.amazon.com/sdkref/latest/guide/feature-process-credentials.html
- **AWS — container/IMDS-style local endpoint:** `AWS_CONTAINER_CREDENTIALS_FULL_URI` / `_RELATIVE_URI` point the SDK at a local HTTP endpoint serving ECS-task-style credential JSON, and `AWS_EC2_METADATA_SERVICE_ENDPOINT` can redirect IMDS lookups to a different host: https://docs.aws.amazon.com/sdkref/latest/guide/feature-container-credentials.html and https://docs.aws.amazon.com/sdkref/latest/guide/feature-imds-credentials.html
- **Off-the-shelf implementation already exists:** `99designs/aws-vault` (MIT, 9,001★, pushed 2025-12-30) ships `aws-vault exec <profile> --server` (`--ecs-server`/`--ec2-server`) that runs exactly this local ECS/EC2-style credential endpoint, and also documents `credential_process = aws-vault export --format=json --no-session <profile>` as a direct drop-in: https://github.com/99designs/aws-vault/blob/master/USAGE.md . This is the strongest "reuse, don't rebuild" recommendation in the cloud-CLI space — the broker can literally embed aws-vault's server mode (or reimplement its small HTTP handler) and mint scoped STS session/role credentials per request rather than exposing the user's long-lived IAM keys.
- **GCP — pluggable/executable-based external-account credentials:** Application Default Credentials (ADC) supports an `external_account` credential-configuration JSON whose `credential_source.executable` field names a local program that ADC invokes and reads a JSON token response from; this requires explicitly opting in via `GOOGLE_EXTERNAL_ACCOUNT_ALLOW_EXECUTABLES=1` for safety. ADC's general search order (env var → `gcloud auth application-default login` file → attached-service-account metadata server) is documented here: https://docs.cloud.google.com/docs/authentication/application-default-credentials . Workload Identity Federation (exchanging an external token, e.g. from AWS/Azure, for short-lived Google credentials via GCP's STS) is documented at https://docs.cloud.google.com/iam/docs/workload-identity-federation-with-other-clouds . The exact executable-protocol field names above come from a secondary summary and should be re-verified against `google-auth-library` docs before implementation — flagged as **moderate confidence**.
- **Azure — Managed Identity / IMDS:** production VMs fetch tokens from the IMDS endpoint (`169.254.169.254`), documented at https://learn.microsoft.com/en-us/entra/identity/managed-identities-azure-resources/how-to-use-vm-token . Azure does **not** document an official local-development equivalent to AWS's `credential_process`; community workarounds point `DefaultAzureCredential`'s `IDENTITY_ENDPOINT`/`MSI_ENDPOINT` env vars at a hand-rolled local HTTP server emulating the IMDS response shape — this is a **community pattern, not an official Microsoft broker**, and should be treated as the weakest-attested of the three cloud mechanisms.
- **General design takeaway:** `credential_process`/IMDS-emulation mechanisms are the *easiest* non-HTTP-MITM win available, because they're explicitly designed as "ask an external trusted program for credentials" — a loopback plaintext call from inside the sandbox to the broker, no TLS interception needed at all, unlike the HTTP(S) MITM approaches in §1.

### Package registries
- **npm:** `.npmrc` scopes `_authToken`/`_auth`/`username`/`_password` to a URI prefix (e.g. `//registry.npmjs.org/:_authToken=...`), explicitly "to ensure npm will never send credentials to the wrong host": https://docs.npmjs.com/cli/v10/configuring-npm/npmrc/#auth-related-configuration . Since this is just an `Authorization`/token header on an ordinary HTTPS request, the same credential-injecting-proxy pattern from §1 applies directly: leave the in-sandbox `.npmrc` token blank/sentinel and bind the real token to `registry.npmjs.org` (or a private registry host) + path in the broker's policy.
- **PyPI/pip:** tokens are conventionally embedded as HTTP Basic-Auth in the index URL (`https://__token__:<token>@upload.pypi.org/...`) or in `~/.pypirc`; the same MITM-and-swap approach applies to the Basic-Auth header on the matching host.
- Both cases benefit from binding the credential specifically to the registry's upload/publish paths (not just the host) to avoid widening the blast radius to arbitrary read endpoints — same host+path+method binding model recommended throughout.

## 3. Token minimization

**Verified facts:**
- **GitHub App user-to-server tokens** are scoped to the **intersection** of what the app was granted and what the authorizing user can access ("if the app was granted permission to write... but the user can only read... the user access token can only read"), default-expire after **8 hours**, and are refreshable via a refresh token: https://docs.github.com/en/apps/creating-github-apps/authenticating-with-a-github-app/generating-a-user-access-token-for-a-github-app
- **Fine-grained PATs** scope to a single user/org, to specific repos within it, with granular per-resource permissions, mandatory expiration, and optional org-required approval — but have **documented, real gaps**: they cannot contribute to public repos the user doesn't own/collaborate on, cannot access Packages, cannot call the Checks API, and cannot span multiple organizations in one token: https://docs.github.com/en/authentication/keeping-your-account-and-data-secure/managing-your-personal-access-tokens
- **OAuth Device Authorization Grant (RFC 8628)** is GitHub's documented mechanism "for apps that don't have access to a web browser," i.e., exactly the "headless sandbox, broker on host does the browser flow" scenario; supports the same 8-hour-expiry + refresh-token (6-month validity, `offline_access` scope) semantics as GitHub App tokens: https://docs.github.com/en/apps/oauth-apps/building-oauth-apps/authorizing-oauth-apps#device-flow

**Recommendation (synthesizing the above, partly inference):** the broker should default to minting **GitHub App installation/user tokens** server-side — shortest-lived and automatically scoped to exactly the repos it's already proxying — rather than injecting the user's long-lived classic PAT. Fall back to fine-grained PATs only for the known gaps (Packages, Checks API, multi-org, public-repo-you-don't-own contributions) that App tokens can't currently cover, and avoid ever injecting a classic PAT if avoidable, since it has no granular scope and the broadest revocation blast radius. The same minimization principle extends to AWS (prefer `sts:AssumeRole`/session tokens over forwarding long-lived IAM user keys — exactly what `aws-vault` already does, §2).

## 4. MCP

- **Docker Sandboxes MCP gateway:** the sandbox's agent sees **one** MCP endpoint; `sbx` manages registered servers, OAuth credentials, and lifecycle on the host. Critically, "local stdio MCP servers run on the host, not inside the sandbox VM" and the docs explicitly instruct: "Treat local MCP servers as trusted host integrations." Remote MCP servers also run outside the sandbox. https://docs.docker.com/ai/sandboxes/mcp-gateway/ and https://docs.docker.com/ai/sandboxes/security/ (MCP gateway traffic / trust-boundary section)
- **gh-aw MCP Gateway spec (draft v1.18.0):** formally defines a "transparent proxy service," requiring stdio MCP servers to be **containerized** (bare command execution is explicitly **NOT SUPPORTED** "because it cannot provide the necessary isolation and portability guarantees"), a headless operational model (config via stdin JSON, secrets via env vars — never argv), an "Authentication & Authorization Layer" in the gateway's own architecture diagram, per-server `headers` for upstream auth, per-server `caCertFile` for custom-CA-trusted upstreams, and an `auth` object for upstream OIDC (§7.6): https://github.github.com/gh-aw/reference/mcp-gateway/
- **Design implication:** an MCP gateway is architecturally the same component as the generic HTTP credential-injecting proxy in §1 — a host-side, already-authenticated broker that fronts multiple backend services — just scoped to JSON-RPC-over-HTTP MCP traffic. Both surveyed implementations keep the actual MCP-server credentials/OAuth tokens host-side and expose only a single pre-authenticated gateway endpoint to the sandboxed agent. The prototype broker should share one credential store and one approval-UI code path between its generic egress proxy and its MCP gateway rather than building two separate systems, and write-capable MCP tools should additionally be routed through a safe-outputs-style validated-action layer (§1, gh-aw) rather than being trusted to perform writes directly.

## 5. Known pitfalls

1. **Proxy-unaware clients.** Many CLIs/libraries ignore `HTTP_PROXY`/`HTTPS_PROXY` or implement their own HTTP stack. mitmproxy's own docs justify its "Local Capture" transparent mode (OS-level eBPF/pf interception, no client config) precisely because "there are applications that bypass the operating system's HTTP proxy settings": https://docs.mitmproxy.org/stable/concepts/modes/ . A production design needs **both** explicit-proxy support for well-behaved clients **and** transparent network-namespace/iptables redirection as a fallback — exactly what gh-aw-firewall does by default (iptables-based enforcement, with an alternative `--network-isolation` Docker-network-topology mode for environments without `NET_ADMIN`): https://github.com/github/gh-aw-firewall/blob/main/docs/usage.md

2. **Certificate pinning.** Any client that pins a certificate or public key (rather than validating against the system trust store) will refuse to connect through **any** MITM-based injector (mitmproxy, Envoy-as-forward-proxy, Squid SSL-bump, smokescreen's MITM mode) regardless of a trusted CA. This is a structural limitation, not a configuration bug — the only general mitigations are (a) excluding pinned endpoints from interception entirely (and denying credential injection there, handling them via a non-HTTP mechanism like `credential_process` instead), or (b) relying on an app's own documented corporate-proxy opt-out if one exists. **[inference from first principles / general TLS-pinning behavior — no single vendor doc states this, but it follows directly from how certificate pinning is designed to work]**

3. **HTTP/2 and WebSockets.** True credential rewriting across a long-lived, multiplexed, or upgraded connection requires the proxy to fully terminate and re-originate HTTP/2 (ALPN negotiation) or the WebSocket handshake, not just rewrite a request line. mitmproxy documents explicit HTTP/2 and WebSocket interception support, whereas simpler CONNECT-tunnel-only tools (plain tokenizer-style proxies, or smokescreen when *not* using its MITM mode) only ever see an opaque byte stream after the `CONNECT` and cannot rewrite anything inside it. **Design implication:** pick a fully MITM-capable engine (mitmproxy, Envoy forward-proxy, Squid SSL-bump, or smokescreen's MITM mode) if credential rewriting inside WS/H2 traffic (e.g., some LLM provider streaming APIs) is required.

4. **DNS exfiltration.** A policy enforced only at the TCP/HTTP layer still leaks via DNS query content itself (subdomain-encoded exfiltration) unless resolution is also policy-controlled. Both surveyed sandbox runtimes already treat this as a live concern: Docker Sandboxes routes "DNS queries [through] the sandbox's internal resolver, which enforces network policy" (https://docs.docker.com/ai/sandboxes/security/defaults/), and gh-aw-firewall restricts resolution to a fixed `--dns-servers` list and offers a `--dns-over-https` sidecar specifically to prevent cleartext DNS bypass (https://github.com/github/gh-aw-firewall/blob/main/docs/usage.md). This confirms the pitfall is already an actively-mitigated, not theoretical, concern in production designs.

5. **Exfiltration via allowed domains** (e.g., pasting the real secret into an approved `github.com` gist). The core defense across every surveyed system is that the **sentinel value itself must be meaningless outside the broker**, and the real secret must be bound to specific host+path+method, not just a host: Docker Sandboxes' `--method`/`--path`/`--query` rule granularity lets `github.com` be allowed for `GET /repos/**` while `POST /gists` remains denied even though the host is allow-listed (https://docs.docker.com/ai/governance/local/network-rules/); Deno Sandbox's literal `<placeholder>` string and Docker's `proxy-managed` sentinel mean copying the in-sandbox value anywhere leaks nothing of value; and tokenizer's sealed `dst`/`fmt` fields are set by the *secret's creator*, not the caller, specifically "so that choice rests with the secret's creator" — i.e., even a fully compromised client inside the sandbox cannot redirect where the real secret gets injected (https://github.com/superfly/tokenizer README).

6. **Replay of surrogates.** Because the broker, not the sandbox, holds the real secret, a captured sentinel is a bearer-capability *within the sandbox's own network namespace* for as long as policy allows the matching host/path — another process in the **same** sandbox could reuse an overheard sentinel. Host/path/method binding limits blast radius but doesn't prevent intra-sandbox replay by itself. Tokenizer's `bearer_auth.digest` mechanism is a concrete, already-implemented mitigation: the sealed secret can require the **caller** to additionally present a matching bearer value before the proxy honors it, so merely observing the opaque `Proxy-Tokenizer` header isn't sufficient for a different process to replay it (https://github.com/superfly/tokenizer README, "Example" section). A prototype broker should adopt an equivalent per-origin (extension/tab/session) binding check, not rely on the sentinel's secrecy alone.

## 6. Recommended concrete broker design for a prototype

### Policy model (per workspace)
A single declarative, default-deny policy document per workspace, modeled on the most expressive schema found (Docker Sandboxes' network rules) plus the credential-binding ideas from tokenizer and smokescreen:
- **`allowed_hosts`**: list of `{host-glob, methods[], path-glob, query-constraints[]}` — directly mirrors `sbx policy allow network api.github.com --method GET --path '/repos/**'` (https://docs.docker.com/ai/governance/local/network-rules/).
- **`credential_bindings`**: list of `{credential_id, host-glob, path-glob, methods[], inject: {dst: header|query, name, fmt}, mode: generic|oauth2|sigv4-resign, ttl, approval_state}` — modeled on tokenizer's sealed `inject_processor`/`sigv4_processor` (https://github.com/superfly/tokenizer) and smokescreen's `MitmDomain.AddHeaders` (code-cited above). The `dst`/`fmt` fields must be set only by the host-side broker, never by the sandboxed caller, replicating tokenizer's explicit design intent.
- **`ssh_bindings`**: `{key_fingerprint, allowed_hosts[], require_confirm: true}` — the simplest version is literally `ssh-add -c` on the host agent (https://man.openbsd.org/ssh-add) plus a thin custom forwarding filter (built on the documented agent wire protocol: https://www.ietf.org/archive/id/draft-miller-ssh-agent-14.html) that raises the editor UI for new key/host pairs, since no maintained off-the-shelf filter (`tiwe-de/ssh-agent-filter` is archived/unlicensed) is production-safe to adopt wholesale.
- **`cloud_credential_bindings`**: for AWS, reuse `aws-vault`'s server-mode approach directly (`--ecs-server`/`--ec2-server`, MIT-licensed, https://github.com/99designs/aws-vault/blob/master/USAGE.md) to mint short-lived STS creds per sandbox; for GCP, a `credential_process`-equivalent executable or pluggable-auth JSON (https://docs.cloud.google.com/docs/authentication/application-default-credentials); for Azure, a hand-rolled loopback IMDS-shaped emulator (no official equivalent exists).
- **`mcp_servers`**: list of upstream MCP servers with their own `headers`/`auth`/`caCertFile`, modeled on the gh-aw MCP Gateway config schema (https://github.github.com/gh-aw/reference/mcp-gateway/) and exposed to the sandbox as one gateway endpoint, matching Docker's "agent sees one MCP endpoint" model (https://docs.docker.com/ai/sandboxes/mcp-gateway/).
- Everything starts **empty/deny**; expansion only happens via an editor-rendered approval prompt (per the brief's "familiar trust/access prompts") that writes a new rule into this document, or via a time-boxed session grant that auto-expires.

### Where the broker runs
As a **host process owned and lifecycle-managed by the editor's main (non-sandboxed) process** — not inside the sandbox runtime, and not merely a library loaded by the remote extension host. Rationale, grounded in what was found:
- Every system surveyed keeps the real secret **outside** the isolation boundary: Docker Sandboxes' proxy is explicitly host-side ("the real credential stays outside the sandbox throughout the request," https://docs.docker.com/ai/sandboxes/architecture/); smokescreen is a standalone mTLS-authenticated service identifying callers by client certificate (https://raw.githubusercontent.com/stripe/smokescreen/master/README.md); gh-aw-firewall's API-proxy sidecar is a separate container from the agent specifically so "LLM API keys... never reach the agent process" (https://github.com/github/gh-aw-firewall README).
- It needs to drive UI approval dialogs that live in the editor's main/renderer process — the same relationship VS Code already has between its main process and a **Remote Extension Host** spawned alongside a remote/container workspace via a small **VS Code Server** component: "the server is automatically installed... [and] VS Code also automatically manages starting and stopping the server" (https://code.visualstudio.com/api/advanced-topics/remote-extensions). The broker should be architected as a *sibling trusted server process* to that remote extension host — spawned/torn down with the workspace's sandbox lifecycle, but never co-located inside the same microVM/container as extension code.

**Reuse the sandbox runtime's own proxy where one already exists.** If the chosen sandbox backend is Docker Sandboxes (`sbx`), it already ships essentially this entire design — host-side sentinel injection, method/path/query-scoped network rules, host-managed OAuth, and a dedicated MCP gateway (https://docs.docker.com/ai/sandboxes/architecture/, /mcp-gateway/, /configuration/credentials/). In that case the fork's job is to **surface** Docker's existing approval/credential primitives inside VS Code's own trust-prompt UI, not reimplement a parallel proxy. If instead a bespoke microVM/container (Firecracker/gVisor/etc.) without a built-in proxy is used, implement the broker as a small process embedding either:
- **`smokescreen`** (Go library, MIT) for environments wanting a single project that natively does both ACL enforcement *and* per-domain MITM header injection (code-verified above) — closest one-stop match, and importable directly as a Go package; or
- **mitmproxy**'s `DumpMaster`/addon API (Python, MIT) if HTTP/2/WebSocket coverage and fast live-policy iteration matter more than raw throughput — fully importable as a library, not just a CLI.

Either way, provision a **locally generated, per-workspace CA** whose certificate is pushed into the sandbox's trust store at boot — the same pattern mitmproxy's `mitm.it` install flow and gh-aw-firewall's `--difc-proxy-ca-cert` both use (https://docs.mitmproxy.org/stable/concepts/certificates/, https://github.com/github/gh-aw-firewall/blob/main/docs/usage.md).

Non-HTTP channels (SSH, cloud CLIs, package registries) are handled by small purpose-built loopback/Unix-socket shims launched by this same broker process and bound only inside the sandbox's network namespace: an SSH-agent filter socket (per above), an AWS `credential_process`/IMDS-style HTTP listener (reusing `aws-vault`'s server code, https://github.com/99designs/aws-vault), and an Azure-IMDS-shaped loopback listener — none of these require TLS interception at all, since they're native "ask a local trusted program for credentials" extension points (https://docs.aws.amazon.com/sdkref/latest/guide/feature-process-credentials.html).

### How the editor UI gets prompt requests
Since the broker is a host-process sibling of the main editor process (same trust zone, per the VS Code Remote Extension Host model above), it should push approval events over the editor's existing local IPC channel (the same channel class VS Code already uses between its main process and the VS Code Server/remote extension host, https://code.visualstudio.com/api/advanced-topics/remote-extensions) rather than inventing a new transport. Every sentinel/binding the broker issues should be tagged with the originating workspace + extension + session id, so the rendered prompt can say "Extension X wants to reach host Y with credential Z," mirroring both the MCP gateway's per-server/per-tool scoping (https://github.github.com/gh-aw/reference/mcp-gateway/) and Docker Sandboxes' per-sandbox policy scoping (`--sandbox <name>`, https://docs.docker.com/ai/governance/local/network-rules/) — and reuses VS Code's existing workspace-trust/extension-permission prompt affordance rather than introducing a new UI pattern, directly matching the brief's request for "familiar trust/access prompts."
